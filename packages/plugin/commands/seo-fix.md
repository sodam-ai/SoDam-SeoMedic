`$1`로 전달된 대상(로컬 폴더 경로 또는 GitHub 저장소 주소)을 대상으로 `seomedic` MCP 서버의 fix 도구들을 사용해 진단→승인→적용 흐름을 진행하라.

## 대상 판별

- `$1`이 로컬 폴더 경로처럼 보이면(예: `./my-app`, `C:\...`, `/home/...`) **로컬 폴더 모드**(아래 "로컬 폴더 절차")로 진행하라.
- `$1`이 GitHub 저장소 주소처럼 보이면(예: `https://github.com/owner/repo`, `github.com/owner/repo`, `owner/repo`) **GitHub 저장소 모드**(아래 "GitHub 저장소 절차")로 진행하라.
- 인자가 없으면 사용자에게 어느 쪽인지(로컬 폴더 경로 또는 GitHub 저장소 주소) 먼저 물어라.

## 로컬 폴더 절차

1. 대상이 로컬 폴더임을 확인한다.
2. `seomedic_fix_plan`(projectRoot=`$1`)을 호출해 계획을 생성하라.
   - 이 단계는 어떤 파일도 수정하지 않는다(dry-run). git 상태가 clean이 아니면 도구가 거부하니, 사용자에게 "git commit 또는 clean 상태로 만든 뒤 다시 시도해달라"고 안내하라.
   - Next.js 프로젝트가 아니면 도구가 거부한다 — 이 도구는 Next.js 소스만 지원하며, 다른 스택은 `/seo-audit`(분석 전용)만 가능함을 안내하라.
3. 계획 결과를 사용자에게 그대로 보여줘라:
   - **자동 적용(add_safe)** 항목은 diff와 함께 "자동으로 적용 예정"임을 알려라.
   - **승인 필요(gated)** 항목은 diff를 반드시 보여주고, 각 항목에 대해 사용자에게 승인/거부 의사를 물어라. 사용자가 승인하면 `seomedic_fix_approve`(fixId), 거부하면 `seomedic_fix_reject`(fixId)를 호출하라. **사용자 확인 없이 임의로 승인하지 마라.**
   - 자동 수정이 불가능한(제안만) 항목은 왜 자동화되지 않는지(예: 동적 계산·sitemap 비어있어 도메인 추론 불가 등) 함께 설명하라.
4. 사용자가 적용을 원하면(승인 절차가 필요한 항목은 3번을 먼저 완료한 뒤) `seomedic_fix_apply`(projectRoot, auditRunId)를 호출해 실제로 파일에 반영하라.
   - 결과에서 `build_failed`가 있으면 이미 자동으로 롤백됐음을 안내하고, 실패 원인(build 에러 메시지)을 그대로 보여줘라.
   - **적용 후에도 "안전한 수정이니 그대로 배포해도 된다"고 말하지 마라** — add_safe도 실제 파일 변경이라 커밋→배포되면 실제 사이트에 반영된다. 커밋 전 diff 재검토를 권하라.
5. 사용자가 적용된 수정을 되돌리고 싶어하면 `seomedic_fix_rollback`(projectRoot, fixId)을 호출하라.

## GitHub 저장소 절차 — 본인 소유 저장소는 검증 완료, fork(남의 저장소)는 실험적(⚠️ 미검증)

1. **진행 전 반드시 사용자에게 알려라**: "GitHub 저장소 자동 수정 중 본인 소유 저장소에 대한 PR 생성은 실제 GitHub 환경에서 검증되었습니다. 다만 본인 소유가 아닌 저장소(fork 경유)는 아직 실제 GitHub로 검증되지 않은 실험적 기능입니다. 진행하기 전에 원치 않는 저장소에 잘못 실행되지 않도록 저장소 주소를 다시 한번 확인해주세요." 사용자가 진행에 동의하지 않으면 멈춰라.
2. `SEOMEDIC_GITHUB_TOKEN` 환경변수가 없으면 도구가 스스로 거부하고 이유를 알려준다 — 사용자에게 토큰 설정 방법을 안내하라(최소 권한 토큰 권장, 절대 대화창에 토큰 값 자체를 입력하지 말라고 안내).
3. `seomedic_fix_github`(repoUrl=`$1`)을 호출하라. **이 도구는 한 번의 호출로 진단→add_safe 자동 적용→PR 생성까지 전부 수행한다** — 로컬 모드와 달리 중간에 gated 항목을 대화형으로 승인받는 단계가 없다(1회성 흐름이라 구조적으로 불가능). 그래서 색인·표시에 영향을 주는 항목은 자동 적용되지 않고 "승인이 필요해 자동 적용하지 않은 항목"으로만 보고된다 — 이 목록을 사용자에게 반드시 보여주고, 필요하면 수동으로 처리하라고 안내하라.
4. 결과에 PR 링크가 있으면 그대로 보여주고, **자동 머지되지 않았음**과 **저장소 관리자가 직접 검토해야 함**을 함께 안내하라.
5. "이미 같은 수정으로 열린 PR이 있어 건너뛰었다"는 결과가 나오면 그대로 안내하고 중복 PR을 만들려 하지 마라.

## 안전 원칙(위반 금지)

- **어떤 경우에도 gated 항목을 사용자 승인 없이 적용하지 마라.**
- git 상태가 clean이 아닌데 강제로 진행하려 하지 마라(도구가 이미 거부하지만, 우회 시도도 하지 마라).
- 이 명령은 **로컬 소스 또는 GitHub 저장소만** 대상이다 — 프로덕션 서버나 배포된 사이트를 직접 수정하지 않는다.
- GitHub 저장소 모드는 **main/master에 직접 push하거나 자동으로 머지하지 않는다** — 항상 새 브랜치+PR로만 제안한다(도구 자체에 강제 push 옵션이 물리적으로 없음).
- GitHub 저장소 모드의 검증 상태(본인 소유 저장소=실제 PR로 검증됨, fork(남의 저장소)=아직 미검증)를 사용자에게 숨기지 마라 — 실행 전에 반드시 알려라.
